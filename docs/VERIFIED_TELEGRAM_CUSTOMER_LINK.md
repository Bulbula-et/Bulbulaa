# Verified Telegram Customer linking — change record (2026-10-15)

## Request and impact

The Google external-browser handoff successfully signs in on Telegram Android and Desktop, but each device has an independent PHP session. Signing in with a different Google identity opens a different Customer. **User decision:** link the Telegram account, with explicit consent from the Google-backed mobile Customer account as primary. Do not merge the other Google account or its saves/reviews.

Verified current code before change: browser handoff bound to the initiating session; `CustomerRepository` resolves Google by verified Google identity/email; `CustomerAuthService` creates independent per-device account sessions; `initData` was UI capability context only; deletion pseudonymizes a Customer and revokes sessions. Impacted: Customer auth, account settings, session revocation, database, official Telegram bridge, CI, production backup/deployment. No Google token or external browser cookie is repurposed.

## Research and dependency decision

- [Official Telegram Mini Apps validation](https://core.telegram.org/bots/webapps): send **raw** `Telegram.WebApp.initData` to the server. For bot-token validation, exclude `hash`, lexicographically order remaining decoded `key=value` fields separated by LF, HMAC-SHA-256 with a secret derived from the bot token using `WebAppData`, compare the digest, and check `auth_date`. Do not trust `initDataUnsafe`, usernames, user-entered IDs, or `surface=tg`.
- [tg/tgwebvalid 4.2.5](https://github.com/CrazyTapok-bit/tgWebValid/tree/v4.2.5) / [Packagist](https://packagist.org/packages/tg/tgwebvalid): MIT, PHP ^8.2, focused framework-free Mini App validator, test suite/CI, release March 2026. Inspected the tagged source (`InitDataValidator`, `Validator`, `Make`, `helpers`): performs the official two-stage HMAC but **does not enforce freshness**, uses `parse_str` (normalizes/collapses field names), and compares hashes with `strcmp` rather than constant-time `hash_equals`. A 256-bit HMAC cannot practically be guessed over the network from this comparison; nevertheless rate-limit, reject duplicate/noncanonical names before parsing, and keep a pinned version. The adapter adds a five-minute age and 60-second clock skew allowance and fails closed. Carbon and seven additional transitive packages (Symfony Clock/Translation components and polyfills, PSR Clock, Carbon Doctrine types) are the deployment cost. They are libraries, **not Symfony Framework**, and Composer install remains ordinary shared-host PHP; no daemon or Redis. Audit the pinned lockfile at each build. GPL-licensed and unlicensed smaller candidates were rejected. No `vendor/` files are committed.
- Google sign-in still uses the existing official GIS verification and browser handoff; verified Telegram auth is **only** for a Customer that explicitly linked that Telegram identity.

## Trust boundary and user flow

1. On the signed-in **mobile primary Google account**, open Account settings in the Mini App. The page displays that Customer's email, an explicit checkbox explaining the link/no merge, and a button to link. Only an ACTIVE account with a verified Google subject ID may be linked. Backend verifies a fresh signed launch with the configured bot token, CSRF and a per-session limiter before a one-to-one insert. Database unique constraints on Telegram identity HMAC and `customer_id` arbitrate concurrent link attempts. Raw Telegram user ID is not stored in the link table; a stable server app secret is required for the HMAC. Losing/rotating this secret means links need re-establishment; never log raw initData or bot token.
2. On another device, a **guest** Mini App session with a fresh verified launch automatically signs into the linked active Customer, regenerates the PHP session ID and starts a revocable account session. An **already signed-in different Customer** receives the linked account name/email and an explicit switch confirmation; no implicit merge, reassignment, or silent logout. Their original Google Customer/data remains untouched. A Telegram user without a link is not granted access and must first sign in via Google (or use other existing methods without link eligibility).
3. A Telegram-authenticated session is checked against its still-present link on subsequent requests. Disconnect from Account settings in **any signed-in browser**, including after Telegram access is lost, by typing `UNLINK`. It revokes **all** this Customer's sessions (origins cannot be distinguished reliably for every legacy session), clears the current session, and requires sign-in again. Permanent deletion also removes the link. Pending-deletion/suspended/deleted Customers never receive an automatic Telegram login or restoration; restoration remains under the separate verified recovery flow.
4. Because signed launch data is a short-lived bearer proof, TLS, same-origin CSRF, no logging, and a 5-minute freshness window are mandatory. A long-open Mini App may need closing/reopening before linking. Signing out ends the local session, **not** the identity link: a subsequent fresh Telegram launch can sign in again. Use **Disconnect Telegram** to remove that capability. Bot-token compromise requires immediate token rotation and link/session incident response; app-secret rotation must be coordinated because identity HMACs change.

## Verification and acceptance

CI uses independently generated HMAC fixtures, then exercises malformed, tampered, stale and wrong-bot launch data, conflicting links, guest cross-device login, explicit desktop switch, separate saved-place ownership, disconnect/session revocation and permanent deletion on SQLite and MariaDB. This is synthetic—not a real Telegram user. Manual owner acceptance: after deployment, sign in to the chosen Google-backed account on Telegram Android, link it in Account settings, reopen Mini App on Desktop signed into the other Google account, confirm the switch, verify the same saves/reviews, and ensure the other account's data has not merged. Test disconnect and re-link only with an owner-approved test account. **Do not perform destructive deletion in production acceptance.** Do not paste initData, cookies, tokens, challenge URLs or personal data into tickets.

Deployment order: green CI on PHP 8.2/8.3/8.4 and MariaDB; verified application+database backup; apply additive migration; install pinned Composer dependencies; deploy code; check migration status and public/login routes; have user test both real devices. Rollback: restore previous code and matching vendor dependencies; retain additive link table until links are independently revoked/retained under an approved migration rollback plan. Do not roll back by dropping live link data without a backup. Existing Google sign-in remains functional if Telegram launch data is absent.
