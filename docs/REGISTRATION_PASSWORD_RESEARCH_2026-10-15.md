# Registration/password change research and approved policy — 2026-10-15

## Scope and observed baseline

The existing `/auth/register` immediately creates an ACTIVE Customer and then attempts to send a separate email-verification OTP. This permits a Customer row before proof of inbox access. The registration page has no Google option although `/auth/login` already has official GIS and Telegram's external-browser handoff. Customer registration, password creation/change and password reset all enforce 12–128 bytes plus uppercase/lowercase/digit; Staff password policy is independent. PHP currently uses PASSWORD_DEFAULT (bcrypt), which silently ignores bytes after 72; the Customer UI previously accepted 128. Authentication and session controls already use CSRF, revocable PHP sessions, PHPMailer, OTP rate limits and server-side Google identity verification.

## External review and package decision

- [NIST SP 800-63B-4, Password Verifiers](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/#passwordver) requires **15 characters for passwords used alone**, permits eight when a second factor is required, disallows composition rules, counts Unicode code points, and encourages common/compromised-password screening, password-manager paste and show-password control. **Owner explicitly chose eight Customer characters without mandatory MFA. This is a documented NIST single-factor deviation**, not a claim of compliance. Email verification during enrollment is not MFA on subsequent password login. Staff policy remains unchanged.
- [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) recommends a strength meter and zxcvbn-ts, no character classes, passphrase/Unicode support. [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) recommends purpose-bound short-lived single-use codes, server-side checks and clear errors; use a consistent password policy across registration/reset/change. A one-time code remains a bearer secret, so never log it, limit attempts and bind it to the requesting PHP session.
- [@zxcvbn-ts/core](https://www.npmjs.com/package/@zxcvbn-ts/core) v4.2.0 (MIT; actively maintained 2026, one runtime dependency) with selective adjacency graphs and English translations (a small local word list keeps the bundle ~50 KB) provides pattern-aware **advisory** strength feedback. Pin dependencies with `package-lock.json`; compile a local, self-hosted static browser asset with build-only esbuild. No Node process or NPM dependencies run on shared hosting; no unpinned CDN. Meter never replaces server validation and never imposes a minimum score. Classic Dropbox zxcvbn is older and much larger; old PHP ports do not improve live browser feedback and add production Composer weight.
- [PHP password_hash](https://www.php.net/manual/en/function.password-hash.php): PASSWORD_DEFAULT is currently bcrypt with a 72-byte input truncation risk. Both local PHP and the production shared host report PASSWORD_ARGON2ID available. Use a small Customer password adapter with Argon2id for new/change/reset hashes, retain password_verify for legacy bcrypt hashes, and avoid truncation; never store plaintext passwords. Check memory/cost on shared hosting.
- The owner narrowed the email design to **one six-digit code only**, no activation link (avoids email-link scanners and external-browser/Mini App session handoff). Email must be sent before any Customer row is inserted; after a valid code is entered in the originating session, create the verified account atomically and sign into that session. Plain-text email only; no advanced template manager now. Production SMTP delivery remains owner-tested, not agent-verified.

## Explicit policy / boundaries

- Customer passwords: 8–128 Unicode characters, no uppercase/lowercase/numeric/symbol composition rule. Exact small server-side denial list only for trivial values (e.g. `12345678`, `password123`), **not** blanket repetition or score enforcement; `12121212` is allowed as requested but meter should label it weak. Staff password rules are untouched.
- Email and name: live format/length/match feedback, no validation request containing a plaintext password; browser-side strength estimation stays local. Never send a password, full password hash or a zxcvbn result to a remote service. Allow paste/autofill; no misleading absolute crack times. Server remains authoritative and shows actionable errors if JS is absent.
- Pending registration remains in a protected server-side PHP session as an Argon2id password hash, normalized email, name, surface, HMAC of the six-digit code, expiry and attempt count. No Customer row before verification. Ten-minute expiry, five failed attempts, resend throttling, and session fixation protection. A fresh code invalidates the previous code. Production mail transport failure means no usable pending registration; development preview may display the code only when existing preview feature gates are enabled. Database unique email prevents races and no Google identity is silently merged.
- Google continuation on signup reuses the same official GIS ID-token verification and Telegram browser handoff as login. A Google-verified identity can sign in/create via that existing flow without a redundant email code. This is separate from password registration.
